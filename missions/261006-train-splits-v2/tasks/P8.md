# P8 design: systems, integration and quality gates
Goal: the technical plan that turns v1 into a v2 driven by integrity, working on any train, plugged into Joel's new
systems, testable offline and in Studio, secure and fast on phones.

Read first: M/refs/context.md, M/refs/v1-kit.facts.md and M/refs/canon-skills.facts.md. Also read sections B and C of
M/refs/roblox-vfx-physics.facts.md.

Write M/design/systems.md (max ~3,000 tokens) with these sections:

1. Kickoff intake:
   - exactly what Joel must export from Studio, and how: the integrity system, his event layer, the Diesel train and its
     split, the TrainSplit modules as he has them now, and the game-over or round flow
   - formats Claude can read: .rbxmx or .rbxlx, or scripts as text
   - how he uploads them to this repo or session
   - what Claude does with them first: a diff against v1, then the contract

2. Integration contract (proposed):
   - the API between the integrity system and the split system:
     - thresholds 70/30/0 in per-train config
     - each threshold fires once
     - if one hit drops integrity past several thresholds, they play in order with a stagger
     - a reset or respawn restores the train
   - events: server to client only
   - the per-train profile registry: break points, tear cells or a "pre-split by owner" mode for the Diesel, chunking
     for the 0% blow-up, fx and sound flavour
   - what replaces v1's hard-coded roof signature and 2-carriage limit

3. Root-cause plan for v1's silent test (from the v1 facts), and how v2 avoids that class of failure: a Studio
   diagnostic command or test bench that prints every step.

4. Test strategy:
   - the Lune offline suite: fix it, then add tests for thresholds, order, idempotence, multi-train, chunking and despawn
   - a Studio test bench: a server-only admin command or an integrity slider, never callable from the client in live
   - a phone performance test: MicroProfiler steps, with budgets from the designs
   - a multiplayer test: 2 or more clients, with latency

5. Security: the points exploit-guard scans (remotes, fling, integrity writes, the admin bench), and the fix patterns.

6. Ops: versioning; Studio install and upgrade steps for Joel (rbxmx); rollback; the release gate (rr-release-train);
   analytics hooks (optional, PROPOSED).

7. Build task list. For each task: deliverable | skill and commands | depends on | model/effort | est. tokens |
   done-when | owner steps.

Reply in at most 10 lines: the path, the integration risks and what Joel must bring.
